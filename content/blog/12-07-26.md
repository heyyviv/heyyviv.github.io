**Narad** is a high-performance, self-hosted log intelligence platform built for microservices. It ingests structured logs with business dimensions via Apache Kafka, stores them in TimescaleDB, and enables cross-service request tracing and dimension querying.

To take Narad from a high-throughput queue-to-db worker to an enterprise-ready log intelligence system, we don't have to reinvent the wheel. We can study the architectures, codebases, and academic papers of industry-defining open-source systems. 

Here is a curated guide to the open-source codebases, specific module implementations, and technical papers that will help us make Narad faster, more reliable, and smarter.

---

## 1. High-Throughput Ingestion & Database Modeling

### Reference: Promscale (TimescaleDB)
*   **The Code:** [github.com/timescale/promscale](https://github.com/timescale/promscale)
*   **Specific Module:** `/pkg/pgmodel`
*   **What to Learn:** Promscale was Timescale's official connector for storing Prometheus metrics and OpenTelemetry logs/traces in TimescaleDB. Although discontinued in 2023, its Go codebase is the absolute gold standard for how to write high-frequency telemetry data to PostgreSQL.
*   **Implementation Detail:** Study how Promscale utilizes the PostgreSQL binary `COPY` protocol via `pgx.Conn.CopyFrom` instead of individual or batched `INSERT` queries. It implements custom batchers and queue workers in Go that accumulate logs in memory (or temporary staging tables) and stream them directly into database buffers. This achieves **50–100x** the throughput of standard inserts.

### Technical Article: "Design Patterns for High-Throughput Ingestion in TimescaleDB"
*   **The Resource:** TimescaleDB Engineering Blog & Technical Documentation
*   **Key Concept:** Data partitioning (chunks) and chronological order insertion. TimescaleDB partitions hypertables on time. Appending logs in loose time-series order allows PostgreSQL to keep only the latest time-chunk index in memory, preventing heavy disk-thrashing random I/O. We must ensure Narad workers batch and sort logs chronologically before flushing them to TimescaleDB.

## 2. Dimension-First / Metadata Indexing

### Reference: Grafana Loki
*   **The Code:** [github.com/grafana/loki](https://github.com/grafana/loki)
*   **Specific Module:** `/pkg/logql` and `/pkg/iter`
*   **What to Learn:** Loki revolutionized logging by choosing **not** to index the raw log text. Instead, it indexes only the metadata/labels (e.g. `service`, `env`, `customer_id`) and stores the raw text compressed in object chunks. This matches Narad's "Dimension-First" philosophy.
*   **Implementation Detail:** Examine how Loki stores and aggregates labels. Their label index maps key-value combinations to chunk references. In Narad, our `log_dims` table is a direct relational analogue to Loki's label store. We can study Loki's query engine to optimize query planner performance when filtering by dynamic key-value maps.

### Technical Concept: ClickHouse Sparse Indexing
*   **Key Concept:** Instead of index lookups pointing to single rows, ClickHouse uses sparse primary indexes that mark the boundaries of data blocks (granules). We can adopt a similar approach to database indexing for `log_dims`. By indexing `(key, value, log_ts DESC)`, we can quickly narrow down the query search space to specific hypertable chunks.

## 3. Distributed Tracing & Context Propagation

### Technical Paper: "Dapper, a Large-Scale Distributed Systems Tracing Infrastructure" (Google, 2010)
*   **The Resource:** Google Technical Report (2010)
*   **Key Concept:** The foundational paper that defines how distributed tracing works: propagating metadata across network boundaries (via headers) using `Trace ID` and `Span ID` to reconstruct a causal chain of events.
*   **Implementation Detail:** Narad implements a `trace_request` endpoint to follow requests across microservices. To make this seamless, Narad should conform to the **W3C Trace Context Specification**. If a log comes in with standard headers like `traceparent` (`00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01`), Narad should automatically extract the trace ID (`4bf92f3577b34da6a3ce929d0e0e4736`) and span ID (`00f067aa0ba902b7`) and register them as native dimensions.

## 4. Pipeline Resilience & Backpressure

### Reference: Vector (by Datadog)
*   **The Code:** [github.com/vectordotdev/vector](https://github.com/vectordotdev/vector)
*   **Specific Module:** `src/buffers` (Rust)
*   **What to Learn:** Vector is a lightweight, ultra-fast observability agent. One of its strongest features is how it handles buffering and backpressure when downstream databases (like TimescaleDB) slow down.
*   **Implementation Detail:** Vector supports dual-mode buffering: fast in-memory queues that spill over to disk-backed buffers (write-ahead log files on disk) when the memory limit is exceeded. We can implement a simplified file-spill buffer queue in the Narad worker. If TimescaleDB experiences a heavy lock or lock wait, the worker can temporarily serialize incoming Kafka batches to local disk files, preventing the consumer lag from growing infinitely and saving system RAM.

## Summary of the Narad Roadmap

By merging the lessons of these systems, we can define a clear path to make Narad a powerhouse:

1.  **Ingestion:** Refactor `InsertLogBatch` to use `pgx.CopyFrom` for native bulk inserts.
2.  **Context:** Auto-parse OTel `traceparent` context format inside our parser pipeline.
3.  **Database:** Run migrations to set up automatic columnar compression and drop-chunk retention policies on TimescaleDB.
4.  **Buffering:** Implement a disk-spill buffer queue in Go for database write failures.
