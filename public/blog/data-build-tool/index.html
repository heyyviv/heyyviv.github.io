Data build tool

30 Jun, 2026 • 4 min read

dbt (data build tool) is an open-source analytics engineering framework that enables data teams to transform data inside the cloud data warehouse using SQL + software engineering best practices.

Key Points:

  • It only does transformation (the “T” in ELT).
  • It runs inside your warehouse (Snowflake, BigQuery, Redshift, Databricks, etc.).
  • It turns raw data into analytics-ready data products.
  • It brings version control, testing, modularity, documentation, and CI/CD to data work.

How it Works in Practice:

  • Raw data is loaded into the warehouse (by Fivetran, Airbyte, Stitch, custom scripts, etc.).
  • dbt transforms it (staging → intermediate → marts).
  • Clean data is consumed by BI tools, data science, applications, or AI models.

A model is a single .sql file that contains a SELECT statement (plus optional configuration). When you run dbt run, dbt compiles that SQL and executes it in your data warehouse to create a table or view.

Key Characteristics of a Model:

  • One model = one logical transformation
  • Written in pure SQL + Jinja templating
  • Stored in the models/ folder
  • Can reference other models or raw sources

What is ref()?

ref() is a Jinja function that tells dbt: “I depend on another model. Please give me its final table/view name and build me after it.”

Basic Syntax:

1select * from {{ ref('stg_orders') }}

Why ref() is Revolutionary:

  • Automatic Dependency Management: dbt builds a Directed Acyclic Graph (DAG) based on every ref() call. It knows the exact order in which models must run.
  • No Hardcoded Table Names: You never write from analytics.stg_orders. You always use ref().
  • Environment Awareness: In development vs production, dbt can use different schemas/databases automatically.
  • Lineage & Documentation: Every ref() creates visible data lineage.

ref() vs source()

Function Used For Example When to Use
ref() Referencing other models {{ ref('stg_orders') }} Almost always for transformations
source() Referencing raw data {{ source('raw', 'orders') }} Only for the very first layer (staging)

2{{ ref('package_name', 'model_name') }}

4-- Using a variable

How the DAG Works:

  • Nodes = Models, Sources, Snapshots, etc.
  • Arrows = Dependencies created by ref()
  • dbt always runs models in the correct topological order.
  • If one model fails, downstream models are skipped.

A materialization tells dbt how to create the output of a model. You define it like this:

1{{ config(materialized='table') }}

Full Breakdown of Materializations:

Materialization What it Creates When to Use Pros Cons Performance
view Database View Lightweight transformations, frequently changing logic Fast to create, always up-to-date Slower query performance Fastest to build
table Physical Table Most final marts, heavy transformations Fastest queries Slower to build, more storage Slow to build
incremental Physical Table (smart) Large tables where only new/changed data matters Best of both worlds More complex to write Excellent for large data
ephemeral Nothing (CTE only) Intermediate logic you don’t want to persist No storage cost Cannot be referenced with ref() from other models easily N/A
materialized_view Materialized View Real-time-ish data with automatic refresh Auto-refresh Warehouse-specific support Varies

3.5 How Models + ref() + Materialization Work Together

This is the core mental model:

  • You write a model (.sql file).
  • You use ref() to declare dependencies.
  • You choose a materialization to control how it gets created.
  • dbt compiles everything into optimized SQL and runs it in the correct order.

Real Example Flow:

stg_orders (view) → int_orders_enriched (table) → fct_sales (incremental)

When you run dbt run, dbt will:

  1. Build stg_orders first.
  2. Then int_orders_enriched.
  3. Then fct_sales (using incremental logic).

3.6 Best Practices for Models, ref(), and Materializations

Golden Rules:

  • One model = One business concept
  • Always use ref() — never hardcode table names.
  • Start with view for staging and intermediate layers.
  • Use table for most marts (unless data is huge).
  • Use incremental only when it gives clear performance benefit.

Name Models Clearly:

  • stg_ = Staging (raw cleaning)

  • int_ = Intermediate (business logic)

  • fct_ = Fact tables

  • dim_ = Dimension tables

  • Keep models small — ideally under 200–300 lines.

  • Use config() block at the top for clarity.

Example of Excellent Config Block:

1{{ config(
2    materialized='incremental',
3    unique_key='order_id',
4    incremental_strategy='merge',
5    on_schema_change='sync_all_columns',
6    tags=['finance', 'daily']
7) }}

1. stg_ – Staging Layer (Raw Cleaning)

  • Goal: Make raw data usable and consistent.
  • This is usually the first layer after raw sources.
  • You should not do heavy business logic here.
  • Focus on: column renaming, data type casting, basic filtering, handling nulls.

2. int_ – Intermediate Layer (Business Logic)

  • Goal: Apply real business rules and combine data.
  • This is where most complex logic lives.
  • You can join multiple staging models here.
  • Often contains calculations that will be reused.

3. fct_ – Fact Tables

  • Goal: Store measurable business events (transactions).
  • These are the tables analysts and dashboards query most often.
  • Usually contain foreign keys to dimensions + numeric metrics.

4. dim_ – Dimension Tables

  • Goal: Store descriptive information.
  • These answer “who”, “what”, “where”, “when”.
  • Often use slowly changing dimension (SCD) logic.
